## Decisions made

**`ADR-0028` — the State Machine Registry is a section of
`KNOWLEDGE-MANIFEST.yaml`.** A state machine is part of the semantic model of
the domain: not project metadata, not build metadata, but knowledge. The
manifest indexes and relates machines; individual specifications remain separate
artifacts. Resolves `ISSUE-0047`.

**`ADR-0029` — Modeling Policy is a first-class artifact type.** ADRs explain
*why* a policy exists; Policies define the rule that must be followed. Unlike an
ADR, a policy is not tied to one decision, is expected to evolve, is normative
rather than historical, and is directly consumed by AI agents. Agents primarily
consume Policies; humans read ADRs for rationale. Resolves `ISSUE-0046`.

## What was learned

**`ADR-0028` gave the three-manifest split a usable decision test.**
`ADR-0013` had separated the manifests by "responsibility and lifecycle", which
was correct but not operational — it did not tell you where a new thing goes.
The answer supplies the criterion: **architecture / implementation status /
semantic structure**. State machines were the first real test, and it resolved
without argument.

**The issue's own preferred option was wrong, and the reason is instructive.**
`ISSUE-0047` judged a separate registry file most likely, on the grounds that
nine-field registrations would be too heavy for a manifest. The weight objection
dissolved once the manifest was scoped to indexing only. A practical objection
was overriding a categorical question — *what kind of thing is this?* — and the
categorical question had the better answer.

**Third instance of `registry indexes, specifications live separately`.**
`MANIFEST.yaml` indexes skills whose specifications live in `skills/`;
`ADR-0027` made the registry an index; `ADR-0028` puts the index in a manifest
and the specifications outside. Three independent arrivals at the same shape is
close to a principle. It should be named as one when the fourth appears —
recorded in `ADR-0028` rather than promoted prematurely.

**`ADR-0029` is the first decision aimed at the corpus itself rather than at the
system being built.** The rationale is arithmetic: 29 ADRs, five superseded, one
partially corrected. Deriving the applicable rules from that history is
archaeology, and it gets monotonically worse. The split — ADRs historical,
policies normative — means the operational specification stops growing with the
decision record.

There is an irony worth recording: **this repository has no policies yet**, so
until M3 the ADR corpus *is* the only statement of the rules. The build state
now says so explicitly for any agent reading it.

**The intended-divergence problem is real and unsolved.** `ADR-0029` says a
policy is expected to evolve past the ADR that created it. So rule text will
exist in two places and *should* differ over time. But intended divergence and
accidental drift look identical in a diff, and nothing distinguishes them
mechanically. Recorded as a negative consequence; it compounds `ISSUE-0048`,
which already showed that supersession and correction cannot express "still true
as history, no longer the operative rule".

**Fourth vocabulary collision, caught on arrival.** "Policy" now names governance
policies, Modeling Policies and process policies. The previous three — "skill",
"authoritative", "state" — were each found late and were expensive. This one was
flagged in the same session it was created (`ISSUE-0050`), which is the first
time the project has caught the pattern before it propagated.

`ADR-0025` solved this class for *state* names by namespacing to the owning
machine. Nothing equivalent governs *artifact type* names, which is the general
form of the question.
