## Decisions made

**`ADR-0120` — engineering understanding is the product metric.** The percentage
of the registered Engineering Question Set that Engineering OS can answer.
Entities, predicates, graph size and proposal count are demoted to
implementation metrics.

**`ADR-0121` — three kinds of Discovery Skill.** `general`, `technology`,
`domain`. **All three produce exactly the same metamodel entities**; they differ
only in how understanding is acquired. A Stack Profile knows *where* a framework
puts things; a technology skill knows *what its presence implies*.

**`ADR-0122` — Engineering OS is a continuously improving engineering memory.**
The first framing of the objective that is a statement about **time**:

> Discovery exists so that six months later an engineer can ask a difficult
> question about a system and receive an answer that nobody had to rediscover.

## What was learned

### The metric flattered the product three times before it was believed

The first version scored `EQ-09` at **`216/216`** — a perfect answer to the
weakest question in the set. Its query is declared `subject: none` and returns
the same rows whatever subject it is handed, so scoring it per subject counted
one answer four hundred and fifty-three times.

The second version fixed that and left the mixed case: a question mapping *one*
model-wide query and *one* per-subject query scored the same way. Fixed by
partitioning.

Then `tools/check-questions.py` was written, and **found a third instance in
`EQ-05` that two rounds of manual review had missed.**

> **A metric is a query too, and it must be validated like one.**

All three defects moved the number **up**. That is the direction metric defects
always take, and it is why the check exists and why the question set is authored
by the reviewer rather than by the implementer.

### `no-query` cannot accumulate, and that changes what evidence means

`ADR-0119` requires the same limitation in several repositories before
Engineering OS may evolve. The measurement made an obvious-in-hindsight
distinction necessary:

- **`no-data`** — a model was built and still could not answer. **Evidence about
  a repository.**
- **`no-query`** — nothing declared even attempts the question. **A constant.**
  It says the same thing about every repository.

`EQ-08` — *who is allowed to perform this operation?* — is `no-query` in both.
**Measuring a hundred more repositories would not advance it by one step.**
Something must first be declared that attempts the question at all.

The reviewer's bar for `DS-authorization-discovery` is therefore precise and
currently unreachable by benchmarking alone, which is a more useful thing to
know than another benchmark would have been.

### The taxonomy caught a misclassification the project had already made

`DS-multitenant-saas` was written as the worked example of a **domain** skill.
Multi-tenancy is not a business. Banking is a business; multi-tenancy is an
**architectural pattern**, and every one of the skill's questions — *which tables
carry a tenant discriminator* — is structural.

**It is easy to believe you are encoding business knowledge when you are
encoding structure**, and a two-box taxonomy made it invisible. Reclassified as
`technology`. **The domain category is empty again, honestly this time.**

### Memory re-ranks the gaps, and authorization is no longer first

`ADR-0122` changes the order of the roadmap by asking which knowledge is
expensive to *rediscover*.

Authorization can be re-read from the code in an afternoon. **The reason a
decision was made three years ago cannot be re-read from anywhere** — the people
who held it have left.

*Why does this system work this way?* scores `no-data` in both repositories, and
under the memory framing it is now the highest-value unanswered question in the
set. That reordering is a consequence of the vision, not of a preference.

### Nothing measures the claim the vision makes

The architecture claims **cumulative** improvement: worth more in month six than
in month one. Continuous and Periodic Reacquisition have run against **one
engineering change, in one repository, over one commit.**

A longitudinal test is now missing infrastructure rather than a nice-to-have,
and it is recorded as the principal gap.

### No strong event-driven candidate is available locally

The next benchmark is to be an event-driven system stressing asynchronous
workflows, eventual consistency, retries, idempotency, dead-letter queues,
message contracts, distributed invariants, sagas and the outbox pattern.

A scan of the available repositories found **one** with a message broker —
`test-plug`, RabbitMQ, 229 Java files and **three test classes**. Since
invariants are discovered almost entirely from tests, that repository would
measure the extractor rather than the engineering shape.

**Recorded rather than forced.** Choosing a weak repository to satisfy a
milestone is exactly what `ADR-0119` exists to prevent.
