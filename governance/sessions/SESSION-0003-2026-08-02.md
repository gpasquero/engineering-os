# SESSION-0003 — 2026-08-02

## Objective

Record three owner decisions — the nature of the framework, the manifest
architecture, and a new foundational principle — and propagate their
consequences.

## Decisions made

**`ADR-0011` — Engineering OS is a knowledge compiler.** Foundational. The
pipeline compiles authoritative assets into a canonical knowledge model, which
is the internal representation and the primary product. Derived artifacts are
produced from the model, never directly from the assets. The website is one
projection among many, alongside knowledge graph, search index, cross-reference
index, impact database, validation reports and **agent context**. Intermediate
representations, incremental compilation and caching are implementation choices,
not architectural requirements.

**`ADR-0012` — executable framework with a typed artifact taxonomy.** Resolves
`ISSUE-0005`. Not a documentation project. Pipelines, validators, generators,
analyzers and visualizers are first-class code. Generated artifacts are never
sources of truth. Pipelines are deterministic. Four artifact kinds:
`authoritative`, `derived`, `runtime`, `cached`. Every generated artifact
declares its inputs, generator, reproducibility and deletability. The build
pipeline continuously verifies that derived artifacts stay synchronized.

**`ADR-0013` — three manifests separated by responsibility and lifecycle.**
Resolves `ISSUE-0030`. `MANIFEST.yaml` (architectural, stable),
`BUILD-STATE.yaml` (implementation state, continuous),
`KNOWLEDGE-MANIFEST.yaml` (knowledge model, per domain change).

## What was learned

**The `ISSUE-0030` question had the wrong axis.** It asked whether one schema
serves two *audiences*. The answer was that audience is not the problem —
**lifecycle** is. Binding content that changes yearly to content that changes
hourly is how a manifest becomes a source of architectural drift rather than a
defence against it. The audience question then dissolves: an adopting repository
has the same three manifests with unused sections left empty.

This also retired the risk `ADR-0009` had recorded against itself — that a
fifteen-concern manifest would become an unmaintainable god-file. It is now
addressed structurally rather than by discipline.

**Second supersession, and the first that narrowed rather than corrected.**
`ADR-0013` supersedes `ADR-0009`. Unlike `ADR-0010`→`ADR-0006`, nothing in
`ADR-0009` was *wrong*: its identity claim survives in full. Only the scope of
`MANIFEST.yaml` narrows, as concerns redistribute. Worth noting that the
supersession mechanism handles both cases without special treatment.

**`ADR-0012` supplies the general solution to a problem recorded twice.**
`ISSUE-0018` (a vocabulary defined in two files) and `ISSUE-0028` (a
hand-maintained index) are the same failure: a derived artifact authored by
hand. The artifact taxonomy names that failure and forbids it, and the build
pipeline's synchronization duty makes it mechanically detectable. Both issues
were updated; neither is resolved yet, because the generator does not exist.

**Determinism collides with the project's own subject matter.** `ADR-0012`
requires deterministic pipelines. Engineering OS is a framework for AI
engineering, and agent output is not deterministic. The likely reconciliation is
that agents *produce* authoritative assets while the compiler *consumes* them —
so an agent-authored artifact becomes authoritative once reviewed and committed,
and its non-determinism is then irrelevant. That reading is coherent but was not
stated, and it leaves open whether agent-produced, not-yet-reviewed output needs
a fifth artifact kind. Recorded as `ISSUE-0033` rather than assumed.

**`ADR-0011` and `ADR-0010` can be read two incompatible ways.** `ADR-0010`
makes `model/` the repository's knowledge model; `ADR-0011` makes the canonical
knowledge model a *compiled output*. Either `model/` is authoritative input and
the canonical model is a build artifact elsewhere, or `model/` is itself the
compiled output. `model-spec/` is an M2 deliverable and cannot be designed until
this is settled — so `ISSUE-0034` is marked `blocking`. Reading A is the more
likely intent but is not confirmed.

**`BUILD-STATE.yaml` duplicates the memory layer.** Its stated content —
milestones, progress, blockers, ADR and issue references — is exactly what
`governance/roadmap.md`, `governance/build-state.md` and
`governance/issues/index.md` already hold. Two artifacts claiming the same
content is the very failure the artifact taxonomy forbids, now at the level of
the project's own status. `ISSUE-0035`. The option most consistent with
`ADR-0001` and `ADR-0012` is that `governance/` stays authoritative and the YAML
is derived — which would close `ISSUE-0028` in the same move — but it was not
assumed.

**`KNOWLEDGE-MANIFEST.yaml` compounds an existing gap.** It declares "glossary
modules", while this project's glossary lives in `governance/`. `ISSUE-0031` was
extended and raised from M11 to also block M2: the overlap must be settled
before the manifest is written, not at self-model time.
