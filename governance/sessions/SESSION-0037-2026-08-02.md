## What was learned

### The confidence conflict was real and the resolution is a distinction

`ADR-0090`: *do not evolve toward confidence scores; engineering evidence is not
probabilistic.* The direction: *workers should emit structured confidence.*

**They govern different objects.** `ADR-0090` forbids Engineering OS from scoring
**its own conclusions**, which it derives deterministically. A worker **is**
probabilistic, and reporting its own uncertainty is the most honest thing it can
do.

The resolution is a **ratchet**: confidence may only add scrutiny. `record` with
medium or low confidence escalates to `govern`; **high confidence never lowers
anything**, because the reason an observation is governed is a property of the
claim, not of the claimant.

**An assertion caught a real leak.** The first implementation stripped confidence
from the accepted path and propagated it through both reject paths — the test was
written to check every exit, and it failed on the first run.

### Real execution produced friction in the first command

`I-modify-behavior` on `Capability.Login` — the obvious reading of *"I need to
add OAuth"* — returned **not-applicable**. `P-change-implementation` applies to
`Artifact`; `P-change-concept` to `Concept`. **Nothing applied to a capability**,
which is what a feature request actually changes.

**This is the first architectural change in the project motivated by friction
rather than by inspection**, which is exactly what `ADR-0102` asks for — and it
happened in the same session the decision was written, without being arranged.

The fix is **data**: one plan. No entity, operator, registry or engine.

### The measurement, on real work

**54 decisions before the first LLM token; 7 left to workers.** Of six tasks,
three require a worker, two are mechanical, one is gated.

The 7 are enumerable: four the plan defers explicitly, three tasks classed
`reasoning`. **The boundary is a list, not a ratio**, and each item can be
examined for whether it could have been derived.

### The audit found something real about ai-desk

`Invariant.TenantIdOnEveryConnection` **has no enforcement point.** ADR-0001
describes it as *"requires discipline: `tenant_id` must be set on every
connection"*, and no artifact in the modelled scope is recorded as enforcing it.

**The system's strongest isolation claim rests on its weakest mechanism**, and
the ADR says so in a sentence nobody would connect to an enforcement question.

A second finding needed the model to exist: `jwt-security.spec.ts` asserts
*"rejects a token with a tampered payload (modified `tid`)"* — **tenant isolation
enforced at the token layer, in a suite that never names the multi-tenancy
decision.** The connection is in neither document.

### Test granularity improved and it mattered

One node per suite with case counts — the change the Kubernetes findings ranked
first — is what made two findings visible. `Q-tests` still names suites rather
than cases, and **it is now useful anyway**, which the file-level model was not.

### Execution Memory: the proposal recommends building almost none of it

Requested before implementation, and **nothing was built.**

The layer is admissible — counts are mechanical, which answers `ADR-0103`'s
question. But `ADR-0102` says change should come from friction, and **nothing has
run twice.** The four example patterns are hypotheses about what will repeat.

**The proposal recommends the run log alone**: it is required by every version of
the layer, it is small, and it turns the aggregation question from a design
exercise into an observation.

Its honest failure mode is recorded: **with few runs, *7 of 9* is
indistinguishable from coincidence**, and a record format displays it with the
same authority either way.
