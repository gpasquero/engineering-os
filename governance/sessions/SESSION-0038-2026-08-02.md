## Decisions made

**`ADR-0105` — Discovery is a workflow.** The Director must never operate
directly on a repository; it operates on an Engineering Model. Brownfield
onboarding and continuous engineering use **one execution architecture**, and
discovery output is **proposals, never authoritative knowledge**.

**`ADR-0106` — the proposed assertion.** A Candidate Engineering Model and an
Execution Observation are the same artifact at different scales.

## What was learned

### The claim was testable, and it holds

> *The only difference between Brownfield and Continuous Engineering is the
> objective. Everything else is identical.*

`I-onboard` on a repository produces a plan, a task graph, worker assignments, a
governance gate and a knowledge-update task **through `tools/direct.py`
unchanged.**

**No execution mechanism was built.** Discovery is declarations in the existing
registries — which is the strongest possible evidence for the claim, because a
correction that required new machinery would not have been a correction.

### The bootstrap is two files

A repository under discovery has no model, and every plan requires a subject that
is a node. **Exactly one node is authored: the repository itself, as an
`Artifact`.**

No special case and no second entry point. The friction that could have appeared
here — *plans need subjects and discovery has none* — did not, because a
repository is already something the metamodel can describe.

### Two problems turned out to be one

`ADR-0105` created a new question: how does a Candidate Engineering Model become
authoritative?

Stripped to structure, it is **the same question the loop has been unable to
answer since `SESSION-0036`**: how does an approved observation become knowledge?

Both are sets of **proposed assertions with provenance, produced by probabilistic
workers, requiring authorization**. They differ in scale and occasion, not in
kind.

**The next build is one mechanism, not two** — and `SESSION-0036`'s log already
predicted its shape, before discovery was on the table:

> *An approved observation becomes an authored assertion, which recompiles like
> everything else.*

### Friction removed a vocabulary instead of adding one

Declaring discovery needed three new actions, and **the action vocabulary was
hardcoded in Python.**

But task kinds already declare `from-action` — so **an action exists because a
task kind derives from it.** The vocabulary is now derived, and a registry that
had been pretending to be a mechanism is gone.

**The session's only code change made the system smaller.**

### The previous session's model was reclassified, not invalidated

`external/ai-desk-auth/` was authored by reading source with `grep` — **a
discovery worker operating without the workflow around it.**

What it contains is what discovery would propose. What is missing is the process:
the plan that requested it, the gates that reviewed it, and the record of what
was proposed and rejected. **It stands as a hand-made Candidate Engineering Model
that skipped its review**, which is a more useful thing to call it than either
correct or wrong.

### The bottleneck the architecture does not solve

**Review does not scale.** A candidate model for a 469-file repository may
propose thousands of assertions, each requiring acceptance.

Batch acceptance is the obvious mitigation and **trades scrutiny for throughput —
exactly the trade `ADR-0023` exists to prevent.** Recorded unresolved rather than
settled speculatively.

**The architecture is correct and the bottleneck is real.** Those are compatible
statements and both belong in the record.
