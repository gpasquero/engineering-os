## What was learned

### The simulation found two defects nothing else could

Both were in **declarations**, not the engine.

**Gate identifiers were written without their `O-` prefix.** `G-decision-record`
declared `required-for-observation-kinds: [assumption-disproved]` where the kind
is `O-assumption-disproved`. It matched nothing, and every governed observation
fell through to the general gate.

> **A registry that names things wrongly is not detectably different from one
> that names nothing.**

Fourteen registries now reference each other and **nothing checks a cross-registry
reference.** That is the deepest finding of the session and it is one line of
debt.

**A gate was declared for an observation kind that is rejected.**
`architectural-concern` never enters the model, so a gate authorizing its entry
is unreachable by construction. The declaration asserted a control that could
never fire.

**Neither was visible to the compiler, the validator, the query schema check, the
parity check or 17 fixtures.** They needed something to run the loop.

### Only two of eight observation kinds may record mechanically

Both are **additive**: confirming an invariant and discovering evidence add
support to what is already asserted. Everything that could change or contradict
an assertion is governed, and the one kind that is purely a worker's judgement —
`architectural-concern` — is **rejected outright**.

That distribution is `ADR-0101` working: the model stays deterministic without
discarding what execution learned.

**An unknown kind was rejected with a diagnostic rather than ignored**, which the
simulation checked deliberately by including one.

### Assignment is under-determined, and correctly so

`T02-change-inspect` matches **four** worker types, including
`W-documentation-writer`, which is plainly wrong for it.

**Capability matching cannot express *the right worker for this kind of
artifact*.** Preferring one would be a heuristic, which `ADR-0099` forbids —
so the system reports all four and the runtime chooses. **The KPI stops improving
at exactly that boundary**, and that is where it should stop.

### The `Concept.Conflict` gap arrived for the third time

Found by a query (`SESSION-0033`), used by a plan as an unmet precondition
(`SESSION-0034`), and now **carried into execution as an UNVERIFIED assumption
that the mocked run disproved.**

One fact has moved through three stages of the loop, changing role each time.
That is the loop working, on the smallest possible example.

### The loop still does not close

`T05-update-knowledge` is assignable and produces a **proposal**. Nothing applies
it: no authorization artifact exists and no path writes an approved proposal into
the model.

**Seven of nine stages exist.** The missing one is the only one that makes the
system better on Tuesday than it was on Monday.

## Recommended next action

Accept or return this session's work.

Then **close the loop**. Two pieces, and the second is the hard one:

**An authorization artifact.** A gate that is passed should produce a record —
`ADR-0021`'s `AcceptanceRecord` is almost exactly this, and the entity already
exists.

**A write path.** An authorized proposal must become model content, and this is
where the architecture has never been tested: **the compiler is the only thing
that writes the model, and it writes from authoring sources.** A proposal is not
an authoring source. Either the proposal becomes one — an authored artifact
someone accepted — or the compiler gains a second input.

**The first option is almost certainly right** and should be tried before the
second is considered: an approved observation becomes an authored assertion,
which recompiles like everything else. That keeps `ADR-0072` intact — the model
is the product and the sources are the input — and makes the loop close through
the mechanism the project already has.
