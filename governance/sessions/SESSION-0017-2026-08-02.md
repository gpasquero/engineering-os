# SESSION-0017 — 2026-08-02

## Objective

Record the owner's acceptance of `SESSION-0016`, settle how dimensions are
specified and constrained, and record the modeling hierarchy that six earlier
decisions turned out to share.

## Acceptance recorded

**`ACCEPT-0012`** — the Project Owner accepted the `SESSION-0016` decisions at
revision `875b853`. Those revisions are now `Active`.

The rationale generalizes the previous session's observation: the project
converges by **separating concepts that were previously entangled**, which is
why disentangling leaves earlier decisions intact rather than superseding them.

## Decisions made

**`ADR-0048` — `DimensionSpecification` is a metamodel entity.** Dimensions must
be specified before they can be instantiated. Ten fields, correcting
`ADR-0041`'s eight. A Dimension Assignment is always an instance of a Dimension
Specification. The initial dimensions are created as instances, not embedded in
compiler documentation. Resolves `ISSUE-0062`.

**`ADR-0049` — dimensions are a scarce architectural resource.** Five conditions,
all of which must hold. Failures are modelled as metadata, a property, a
relationship, or a metamodel entity. **Creating a Dimension requires an ADR.**
Resolves `ISSUE-0064`.

**`ADR-0050` — the `Definition → Instance → Assignment → Projection`
hierarchy.** One recurring pattern across dimensions, state machines and
policies, to be documented as a metamodel pattern and used to evaluate future
extensible concepts.

## What was learned

**A three-session deferral ended by reframing rather than by answering.**
`ISSUE-0062` had carried the four undefined dimensions through `ISSUE-0057` and
`ISSUE-0059`. `ADR-0048` does not define them — it makes them *unwritten
instances of a defined entity* rather than undefined concepts. Combined with
`ADR-0049`'s five conditions, the test that was missing now exists.

Worth being precise about what changed: the four are still not written. What
changed is that writing them is now specified work with a criterion, instead of
a question nobody could answer.

**Two answers arrived as tools rather than verdicts.** Neither `ADR-0048` nor
`ADR-0049` says whether `Governance Status` is a dimension, or whether
Representation is one. Both supply the means to decide. That is a different kind
of answer from the previous sessions, and it moves the work rather than closing
it — `ISSUE-0065` now holds nine candidates, **five of which are already in
active use without ever having been tested**.

**`ADR-0050` is the sixth arrival at a recurring shape, and the second named as
a pattern.** `ADR-0031` named the Registry Pattern after three arrivals;
`ADR-0028` had predicted that naming. This hierarchy spans further — it absorbs
registration, specification, instantiation and assignment into four stages
covering dimensions, state machines and policies at once.

**The Policy row is a prediction, not a description.** `Policy Assignment` is
marked *future, if needed*. That is the same pre-commitment `ADR-0044` made for
Inference Rules: fix where a thing would go before anyone needs it, so the
shortcut of improvising is closed.

**Naming the pattern immediately exposed what it does not cover.** `ADR-0032`'s
Registry Specification is not any of the four stages — it governs the registry
that holds them. The same Registry Projection now appears in two different
pairings, which cannot both be complete. `ISSUE-0066`.

**Fifth correction, and the mechanism is still missing.** `ADR-0048` corrects
`ADR-0041`'s field list from eight to ten. `ISSUE-0048` has been open since
`SESSION-0008`, and a reader arriving at `ADR-0041` still sees eight fields with
nothing in its front matter to indicate otherwise. Five instances is no longer
an anomaly.
