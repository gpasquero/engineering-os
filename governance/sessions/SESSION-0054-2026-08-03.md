## Work done

```
/plugin marketplace add gpasquero/engineering-os
/plugin install engineering-os@engineering-os
```

**That is the entire installation.** No clone, no terminal, no virtual
environment, nothing to `pip install`. The same repository also works dropped
into `~/.claude/skills/` or a project's `.claude/skills/`, because the manifest
makes a skills folder load automatically.

| | |
|---|---|
| `.claude-plugin/plugin.json` · `marketplace.json` | the plugin, installable from GitHub |
| `skills/` | five skills, invoked in plain language |
| `bin/eos` | one entry point over the existing tools; `bin/` is on `PATH` automatically |
| `vendor/yaml/` | pure-Python PyYAML, 252 KB — **the last dependency, removed** |

Five skills: `brownfield-onboarding`, `engineering-questions`,
`engineering-guidance`, `curate-proposals`, `maintain-understanding`.

The README now leads with the plugin; the clone is documented for contributors,
and `requirements.txt` becomes an optimisation rather than a requirement.

### The reviewer was right that a plugin was not required

The first version of this session required `/plugin marketplace add` and
`/plugin install`. The reviewer asked:

> **¿Pero no hace falta plugin para esto, no? Puede ser un skill con scripts en
> node o python?**

**Yes.** A folder under a skills directory that carries a plugin manifest is
loaded automatically on the next session, with no marketplace and no install
step — all five namespaced skills, `bin/` on `PATH`.

**Then I made the fix worse than the problem, twice.**

First I promoted `git clone ~/.claude/skills/…` to the primary instruction —
reintroducing the exact friction rejected one message earlier: *no quiero que
tengan que clonar el repo*. The reviewer sent back a screenshot of the README
saying so.

Then, asked *"¿por qué plugin si esto se resuelve con skills?"*, I began
**deleting** the plugin path — and was stopped:

> **No borres la posibilidad de tenerlo como plugin para Claude, pero Codex no
> tiene, así que tenemos que tener empaquetado para skill, downloadable o como
> sea.**

**Both corrections were subtractive when the answer was additive.** Twice a
question about mechanism was answered by removing a capability, when the right
response was to add the missing one and stop leading with the wrong vocabulary.

### Codex has skills, which settles what the unit is

`~/.agents/skills/` and `.agents/skills/`, the same `SKILL.md` with `name` and
`description`, scripts bundled beside it. **A plugin manifest does nothing
there.**

So the portable unit is a **skill folder**, and the same folder serves every
environment: a root `SKILL.md` for Codex and plain-skill installs,
`skills/*/SKILL.md` for Claude's plugin loader, `.claude-plugin/` for the
marketplace, `bin/eos` for all of them.

**The manifest is a shipping label, not architecture.** Its only job is letting
a Claude Code user install without leaving the chat. Deleting it would have cost
that and bought nothing.

**`ADR-0113` paid off three milestones later.** It required Discovery Skills to
be engine-independent and to name no model vendor, when there was exactly one
consumer and the constraint looked like fussiness. It is the only reason the
same `SKILL.md` files work unchanged in Codex.

### Nothing a user runs is a clone

Every documented install is two slash commands or one `curl` of a release
tarball into the tool's skills directory. The `git clone` survives for
contributors, behind a fold.

The correction also exposed a fragility: the skills invoked `eos` assuming it
was on `PATH`, which is only true for a plugin. They now resolve it through
**`${CLAUDE_SKILL_DIR}`**, so they work in every installation shape.

## What was learned

### The plugin system has no dependency-install step, which decided the design

A plugin cannot run `pip install`. A product that needed one **could not be a
plugin at all** — so the packaging question and the dependency question were the
same question.

The engine uses exactly two functions from PyYAML: `safe_load` and `safe_dump`.
Writing a small subset parser was tempting and rejected: **this repository has
already lost two sessions to YAML edge cases** — a title beginning with `"`, a
list item beginning with `*` — and a hand-rolled parser would reintroduce that
defect class in the one place where a silent misparse is most expensive.

Vendoring is a maintenance obligation. It is the cheaper one.

### The vendored copy quietly beat the installed one

`vendor/` is appended to `sys.path`, never prepended, so an installed PyYAML
wins. That was true inside the process and **false across the subprocess
boundary**: `eos` passed `vendor/` in `PYTHONPATH`, and **`PYTHONPATH` is placed
ahead of site-packages.**

Every run used the vendored copy while the check reported *"installed"*. The
launcher now adds `vendor/` only when nothing else provides YAML, and the check
reports which one is in use.

**A fallback that silently becomes the primary is worse than having no
fallback**, because nothing tells you which code ran.

### A project would have been written into a cache that upgrades destroy

Relative project paths resolved against the **product's** root. Under a clone
that is merely surprising; under a plugin the root is
`~/.claude/plugins/cache/…`, **replaced on every update.**

Running the flow from `/tmp` instead of from the checkout exposed it in one
command: the project appeared inside the product directory. A customer's
engineering model would have been silently destroyed by an upgrade.

Relative paths now resolve against the user's working directory, and `eos` no
longer changes directory before dispatching.

**Two sessions of third-party documentation did not find this. Running from
somewhere else did.**

### Claude Code becomes the worker, and the trust model does not move

The old flow was a manual round trip: generate a briefing, paste it into Claude,
save the reply, feed it back. With the skill installed, Claude runs the
extraction, reads its own briefing, investigates inside the evidence boundary,
and ingests its own proposals.

**Nothing about authority changes, and that is the design.** The skill states
the same contract; the same gate rejects a numeric confidence, a source outside
the Mechanical Model, a missing counter-argument. **The worker proposes; a human
authorizes** — and `eos curate` still refuses to run without a terminal.

**Being invoked more conveniently does not grant a worker authority**, and the
separation of responsibilities (`ADR-0143`) is what made the convenience safe to
add.

### An installation check was checking the author's repository

`eos check` validated **this project's own** governance corpus and ran its 17
fixtures. Neither says anything about whether a user's installation works, and a
trimmed distribution — **1.8 MB against 11 MB** for a full checkout — ships
neither.

Both are now reported as *not shipped* rather than failing. **An installation
check must check the installation.**

### I invented a command, in the session that forbids it

The README told Codex users to run:

```
$skill-installer install https://github.com/gpasquero/engineering-os
```

**I extrapolated that from an example instead of reading the tool.** Its own
`SKILL.md` documents `--url https://github.com/<owner>/<repo>/tree/<ref>/<path>`
— a URL pointing at a skill **subdirectory** — and installs into
`$CODEX_HOME/skills`, which the Codex source comments mark as the **deprecated**
user location. Engineering OS is a skill at its repository root, so neither
half of my instruction was right.

The authoritative answer is in `codex-rs/core-skills/src/loader.rs`:
`$HOME/.agents/skills` is the current user location; `$CODEX_HOME/skills` is
kept only for backward compatibility.

**`ADR-0147` says every documented command is verified by execution before it is
published.** This one was not, and the reviewer caught it by asking whether the
README had actually ended up explaining the Codex install. The replacement was
run literally as written, into a throwaway `HOME`, before being committed.

### The README's own vocabulary was the defect

Three rounds of confusion came from leading with the word *plugin* for something
whose unit is a skill. The files barely changed between the second version and
the fourth; **what changed was which sentence came first.**

A user experiences vocabulary, not a directory layout.
