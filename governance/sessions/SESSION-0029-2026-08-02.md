## Decisions made

**`ADR-0080` — the product is semantic answers to engineering questions.**

> Engineering OS is not being built to compile Markdown. It is being built to
> become the semantic operating system used by developers **and AI agents** to
> understand, reason about, evolve and operate software systems.

Every capability is now evaluated against: *how does this improve a developer's
ability to understand, modify or evolve a real software system?* If the answer is
weak, defer it. The project now has **three admission tests at three levels** —
entities (`ADR-0067`), remaining metamodel entities (`ADR-0075`), and
capabilities (this decision).

**`ADR-0081` — the CKM is the platform's semantic intermediate representation.**
Every future component is a producer or a consumer. **No component rebuilds
semantic understanding independently.**

**`ADR-0082` — the vertical slice replaces metamodel completion as the
milestone.** Seven developer questions define the product. Real-world validation
follows.

**`ADR-0083` — registries are declared.** The compiler knows extraction kinds,
never registry shapes.

## What was learned

### Six of seven questions are answered; the seventh is the finding

*Which AI workflow should execute?* is **not answerable**, and the reason is
sharp: nothing in the metamodel connects **a kind of change** to **a workflow that
should handle it**.

`Policy.governs` points at a Workflow but is not conditional on a change.
`EngineeringGate` reviews but does not select.

**The missing concept is a trigger** — and `ADR-0068` registered `triggers` as a
core relationship type, which **no entity uses**. A registered vocabulary entry
with no user was a dormant signal that something was missing, and it took a
question nobody could answer to notice.

`ADR-0082` predicted two questions might fail. One succeeded. This is the other.

### Two entities were avoided by asking the question first

*Which tests must change?* and *which specifications become inconsistent?* are
both answered — **without a `Test` entity or a `Specification` entity.**

A test is an `Artifact` that `validates` another. A specification is an `Artifact`
that `represents` a Concept. Neither would introduce a relationship the
vocabulary lacks, so neither passes `ADR-0067`.

**Building the slice was cheaper than the entities it made unnecessary**, which
is the strongest evidence yet for `ADR-0080`'s ordering.

### The registry refactor changed the product without changing behaviour

Consolidating three readers into declared registries produced a `12 failure(s)`
run in which every diff was **key order** inside the CKM's vocabulary. The
content was identical.

**Extraction order was leaking into the product.** An IR whose field order depends
on how a registry happened to be parsed is not a stable contract (`ADR-0081`), so
key order is now normalised in `ckm/build`.

Only the golden-output tests could have caught this. No behavioural test would
have — nothing behaved differently.

### `membership` and `extension` were required for seventeen sessions and never written

`ADR-0032` has required every registry to declare both since `SESSION-0011`. **No
registry had ever declared either.**

Writing them raised a question no reader had asked: *may an adopting repository
add Layer A entity types?* The answer is no (`ADR-0037`) and it had never been
recorded where anyone would look for it.

### The slice demonstrates decisions rather than asserting them

`Invariant.SingleCurrency` has no `enforced-at` and `ask.py unenforced` lists it.
`ArtifactRevision.Payment.r3` has no acceptance and `status` reports
`active=False`. `ADR.004` is superseded and `rationale` reports that the decision
establishing an invariant **no longer stands**.

Five sessions of decisions composed into a working model with no special-casing.
