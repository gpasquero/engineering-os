# SESSION-0012 — 2026-08-02

## Objective

Record the owner's acceptance of `SESSION-0011`, establish the Engineering OS
Metamodel, and record its consequence for the order of M2.

## Acceptance recorded

**`ACCEPT-0007`** — the Project Owner accepted the `SESSION-0011` decisions at
revision `ef8e067`. Those revisions are now `Active`.

The rationale marks a phase change: the project has **transitioned from building
governance mechanisms to defining the first elements of the Metamodel**. Eleven
sessions built the mechanisms by which this project remembers, decides and
accepts. From here it describes what it is about.

## Decisions made

**`ADR-0035` — the Engineering OS Metamodel.** The ontology of Engineering OS
itself: not a description of software systems, but a description of *how
Engineering OS describes software systems*. Around twenty entities, each
declaring identity, purpose, ownership, lifecycle owner, authoritative
representation, derived representations, relationships and extension points.
**Every new concept must be positioned in the metamodel before a new artifact
type is introduced.** Resolves `ISSUE-0054`.

**`ADR-0036` — the Canonical Knowledge Model conforms to the Metamodel.** Not an
arbitrary graph. The compiler progressively instantiates the metamodel, which is
**the contract between authoring and compilation**, and must exist **before the
compiler interface is finalized**.

## What was learned

**The process gate inverts eleven sessions of practice.** Until now, a concept
appeared when a problem demanded it and was named afterwards. That produced five
overloaded terms — "skill", "authoritative", "state", "policy", "registry" —
each caught after it had propagated. `ADR-0032` had recorded the recurrence as
the finding. `ADR-0035` is the structural remedy: position first, name second.

Whether it holds is the interesting question. It is a discipline, not a
mechanism, and nothing enforces it until validators exist.

**`ADR-0036` reordered M2 and cost it its readiest deliverable.** The compiler
interface specification was unblocked and was the largest thing available to
build. It is now gated on a metamodel that does not exist and has no home.

The reason is sound and worth restating: if the interface came first, the
compiler would define its own internal structure and the metamodel would arrive
afterwards describing whatever got built. `ADR-0017`'s promise of multiple
implementations would then be unachievable, since a second implementation would
have to reproduce the first's internals.

**The metamodel makes conformance testable, which two earlier ADRs needed.**
`ADR-0017` promised a stable compiler interface; `ADR-0019` made package
conformance the test for federation. Neither had anything to conform *to*. The
metamodel supplies it, and the same decoupling now runs the length of the
pipeline.

**The entity list contains concepts this project has never defined.** Capability,
Concept, Validation and Ontology appear in the metamodel with no ADR, no
specification and no agreed meaning here. Writing the metamodel is design work,
not transcription, and the twenty-item list understates it.

**`ISSUE-0055` and `ISSUE-0031` are one question from two sides.** Is the
metamodel Layer A or Layer B? `ADR-0035` calls it "the ontology of Engineering OS
itself", which sounds like Layer B. `ADR-0036` makes it a contract every
implementation satisfies, which is Layer A. `ADR-0010` keeps repository-local
knowledge local — but every adopter's canonical model must conform to the
metamodel, so it cannot be purely local.

The most coherent long-term answer — authored in `model/`, distributed as a
Knowledge Package — would make the metamodel the first real use of federation,
and is blocked for eleven milestones. The workable answer for M2 is Layer A.
Recorded rather than assumed.
