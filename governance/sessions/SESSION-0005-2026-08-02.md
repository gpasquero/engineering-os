# SESSION-0005 — 2026-08-02

## Objective

Record the owner's answers on acceptance and on Knowledge Packages, and
propagate their consequences.

## Decisions made

**`ADR-0018` — acceptance confers authoritative status.** Supersedes `ADR-0015`.
Authoritative status is determined by an explicit acceptance process, not by who
created an artifact and not by a commit. Six-state lifecycle: Draft → Under
Review → Accepted → Authoritative → Superseded → Archived. Three conditions:
explicit reviewer approval, traceability to the motivating issue or ADR,
successful validation of applicable deterministic checks. **Self-certification
prohibited** unless an explicit governance policy enables it. Acceptance is
itself knowledge, and traceable. Resolves `ISSUE-0009`.

**`ADR-0019` — Knowledge Packages are a published interface.** A package never
exports authoritative assets; it exports a stable projection derived from the
canonical model, and is itself a derived artifact. Its format is a stable,
versioned specification **independent of the compiler implementation**.
Resolves `ISSUE-0029`.

## What was learned

**Fourth supersession, and the first one triggered by a defect this project
found in itself.** `SESSION-0004` recorded that nothing prevented an agent from
committing its own output and self-certifying it as authoritative. `ADR-0015`
had made that possible by treating the commit as the boundary marker.
`ADR-0018` moves the boundary to acceptance and supersedes it. The determinism
principle survives untouched; only the marker moved.

**`ISSUE-0009` was answered by reframing it.** It had asked *who holds authority
at a gate*. The answer says the question is what acceptance **is** — a
first-class engineering concept that must be modeled explicitly, rather than a
role assignment. Worth noting for future issues: a question that resists
answering for several sessions may be the wrong question.

**`ADR-0019` closed the coupling hazard raised in `SESSION-0004`.** The concern
was that a package derived from the canonical model would carry a version
depending on the compiler version. The answer decouples them completely: the
package format is a published specification, and compilers conform to it rather
than define it. This also makes `ADR-0017`'s multiple-implementations promise
testable, since conformance now has something to measure against.

**A vocabulary collision was created and caught immediately.** `authoritative`
is now both a lifecycle state (`ADR-0018`) and an artifact kind (`ADR-0012`).
This is the same class of defect as the overloaded word "skill" resolved in M1 —
and that one survived undetected through the entire inherited corpus. Raised as
`ISSUE-0038`, marked `blocking`, because both vocabularies are early M2
deliverables.

The lifecycle also lists `Accepted` and `Authoritative` as separate states
without saying what distinguishes them. Folded into the same issue.

**The repository now fails its own foundational rule.** `ADR-0018` requires
every authoritative artifact to carry an acceptance record with a reviewer.
Every artifact here — all nineteen ADRs, including `ADR-0018` itself — was
authored by an agent and committed by that same agent. `ISSUE-0040` records
this as a live compliance gap, not a hypothetical, and notes the circularity:
`ADR-0018` cannot accept itself, so whatever resolves this must state its own
base case.

**Two escape hatches were named with nothing behind them.** `ADR-0018` permits
automated acceptance "through explicitly configured governance rules", and that
mechanism does not exist (`ISSUE-0039`). Its third acceptance condition requires
deterministic checks that will not exist until M9 (`ISSUE-0041`). Both were
recorded rather than assumed away — but the second one needs an answer
immediately, because it determines whether *any* artifact can be accepted before
M9.
